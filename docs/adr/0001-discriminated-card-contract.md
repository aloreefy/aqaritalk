# Discriminated-union card contract for broker chat replies

The broker's `/chat` response and the app's stored assistant messages carry rich UI content as a `cards` array of `{type, ...payload}` union members (`properties`, `contact`; `booking` reserved for a later round) instead of the original single-purpose `propertyIds` field. The broker sends IDs; the Node API hydrates them into full records before storing/serving. Chosen so each new agent tool that produces UI (contact card, booking composer) adds a union member instead of a new top-level field, and so the web can switch on `type` and ignore unknown card types from newer backends. New messages write only `cards`; the web keeps read-only support for the legacy `properties` field so conversations stored before this change still render. The broker→Node `propertyIds` field is dropped in the same release — the Node API is its only consumer.
